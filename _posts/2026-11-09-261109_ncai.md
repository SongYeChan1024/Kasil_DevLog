지난 시간에는 함수(Function)로 기능을 나누는 것까지 봤음\
오늘은 그 함수들을 **누가 하는 행동인지** 기준으로 묶는 클래스(Class)로 넘어감

새로 만든 `06.Class/Class.cs`, `06.Class/Class1.cs` 두 파일 정리\
`Class.cs`는 Player·Enemy로 클래스와 캡슐화, `Class1.cs`는 아파트로 생성자·종료자 예제

## Chapter 01. 함수만으로 게임 짜기

### 기능 4개

게임을 하나 만든다고 가정\
Player, Enemy 두 종류만 있음

1. Player가 Enemy를 때리는 기능
2. Enemy가 Player를 때리는 기능
3. Player가 변신하는 기능
4. Enemy가 쓰러지는 기능

지난 시간에 배운 대로 기능 하나에 함수 하나씩 만듦

```csharp
void PlayerAttack()
{
    Debug.Log("플레이어가 적을 때림");
}
void EnemyAttack()
{
    Debug.Log("적이 플레이어를 때림");
}
void PlayerTransform()
{
    Debug.Log("플레이어가 변신중");
}
void EnemyKnockDown()
{
    Debug.Log("적이 쓰러짐");
}
```

지금은 4개라 괜찮은데\
요구사항이 늘어나면 함수가 계속 한 곳에 쌓임\
공격력·체력 같은 정보도 누구 것인지 따로 관리해야 해서 점점 복잡해짐

### 객체 지향 프로그래밍(OOP)

그래서 나온 생각이 **행동의 주체별로 분류를 나눠서 개발하자**\
그 분류를 나누기 위해 등장한 개념이 `class`\
class 별로 프로그램을 만드는 방식을 객체 지향 프로그래밍(OOP)이라고 부름

> 객체 지향 프로그래밍(OOP) : 클래스와 객체를 활용하여 프로그램을 설계하는 방법

함수는 “무엇을 하는가”로 나눴다면\
클래스는 “누가 하는가”로 한 번 더 묶는 느낌

## Chapter 02. Player, Enemy로 분류하기

### 각자 가지고 있어야 하는 정보

| | Player | Enemy |
| --- | --- | --- |
| 정보 | 공격력, 체력 | 공격력, 체력 |
| 정보 | 몇 초 동안 변신할지 | 몇 초 동안 기절해 있을지 |
| 기능 | 때리기, 데미지 받기 | 때리기, 데미지 받기 |
| 기능 | 변신하기 | 넉다운 당하기 |

변수(정보)와 함수(기능)를 같이 묶은 게 클래스\
class는 **사용자 정의 자료형**이라고도 부름\
`int`, `float`처럼 이미 있는 자료형이 아니라 내가 직접 만든 자료형이라는 뜻

### 설계도 코드

```csharp
class Player
{
    public float attackDamage = 10f;
    float healthPoint = 100f;
    float transformDuration = 1f;

    public void AttackEnemy()
    {
        Debug.Log(" Player가 " + attackDamage + "의 데미지를 입힘");
    }
    public void PlayerTakeDamage(float damage)
    {
        healthPoint -= damage;
        Debug.Log(" Player 데미지 받은 hp: " + healthPoint);
    }
    public void StartTransform()
    {
        Debug.Log(" Player가 변신중. . ." + transformDuration);
        AddDamage();
    }
    // AddDamage는 Chapter 05에서
}

class Enemy
{
    float attackDamage = 10f;
    float healthPoint = 100f;
    float KnockDownTime = 3f;

    public void AttackPlayer()
    {
        Debug.Log(" Enemy가 " + attackDamage + "의 데미지를 입힘");
    }
    public void EnemyTakeDamage(float damage)
    {
        healthPoint -= damage;
        Debug.Log(" Enemy 데미지 받음 hp: " + healthPoint);
    }
    public void KnockDown()
    {
        Debug.Log(" Enemy가 넉다운 당함. . ." + KnockDownTime);
    }
}
```

`MonoBehaviour`를 붙인 `public class Class`와 같은 파일 아래쪽에 따로 만듦\
Player, Enemy는 MonoBehaviour를 상속하지 않는 그냥 C# 클래스

### 멤버 변수와 지역 변수

클래스 중괄호 바로 안에 만든 변수 = **멤버 변수**\
클래스의 전역 변수라고도 부름

변수의 생명주기\
중괄호 안에서 만들어진 변수는 그 중괄호가 끝나면 없어짐\
그래서 함수 안에서 만든 `int a = 0;` 같은 건 지역 변수, 함수가 끝나면 사라짐\
멤버 변수는 객체가 살아 있는 동안 계속 남아 있어서 여러 함수가 같이 씀

`healthPoint -= damage;`를 해 두면 다음에 또 맞을 때 줄어든 체력에서 이어서 깎이는 것도 이 때문

## Chapter 03. 객체 만들고 사용하기

### new로 실제로 만들기

```csharp
private Player player = new Player();
private Enemy enemy = new Enemy();
```

class는 설계도일 뿐이고 `new`를 해야 실제 객체가 생김\
Start 안이 아니라 클래스의 멤버 변수로 만들어 둠

### 멤버 접근 연산자 `.`

```csharp
player.AttackEnemy();
enemy.EnemyTakeDamage(10f);
enemy.AttackPlayer();
player.PlayerTakeDamage(10f);
player.StartTransform();
player.AttackEnemy();
enemy.EnemyTakeDamage(90f);
enemy.KnockDown();
```

`객체.함수()` 형태로 그 객체가 가진 기능을 씀\
player가 가지고 있는 `AttackEnemy()`를 쓰고 싶으면 `player.AttackEnemy()`

### 실행 결과

Unity 밖에서 같은 코드를 C# 콘솔(.NET 9.0)로 돌려서 순서 확인해 봄

```text
플레이어가 적을 때림
적이 플레이어를 때림
플레이어가 변신중
적이 쓰러짐
 Player가 10의 데미지를 입힘
 Enemy 데미지 받음 hp: 90
 Enemy가 10의 데미지를 입힘
 Player 데미지 받은 hp: 90
 Player가 변신중. . .1
100
 Player가 100의 데미지를 입힘
 Enemy 데미지 받음 hp: 0
 Enemy가 넉다운 당함. . .3
120
140
```

위 4줄은 Chapter 01의 함수 버전\
변신하면 `AddDamage()`가 같이 불려서 공격력이 10 → 100이 됨\
그 뒤 공격 로그가 `100의 데미지`로 바뀐 걸 보면 player 객체 안의 값이 계속 유지되는 게 보임

하나 걸리는 부분\
`enemy.EnemyTakeDamage(10f)`, `(90f)`처럼 데미지 숫자는 Start에서 직접 넣고 있음\
Player의 attackDamage가 100이어도 Enemy가 받는 건 90\
공격력이랑 받는 데미지를 연결하는 건 아직 안 한 상태로 보임

## Chapter 04. NullReferenceException

### new를 하면 어디에 생기나

- `new Player()` → Player 객체가 메모리의 **Heap** 영역에 생성됨
- `player` 변수 → Heap에 생긴 객체가 **어디 있는지(주소)** 를 들고 있음

변수 안에 객체가 통째로 들어가는 게 아니라 위치 정보만 들고 있는 것

### null

class 자료형으로 만든 변수에는 기본값으로 `null`이 들어 있음

```csharp
private Player player = null; // new를 안 하면 이 상태
```

null은 “가리키는 객체가 없음”\
이 상태에서 `player.AttackEnemy()`를 부르면 찾아갈 객체가 없어서 에러가 남\
이 에러가 **NullReferenceException**

콘솔에서 null인 Player로 함수를 불러 보니 실제로 `NullReferenceException`이 나옴

### stack 이야기

수업 주석에는 player 변수가 stack 영역에 있다고 적혀 있음\
찾아보니 stack에 놓이는 건 함수 안에서 만든 **지역 변수**일 때 기준인 듯\
지금 코드처럼 멤버 변수로 만든 player는 `Class` 객체 안에 같이 들어 있음\
어느 쪽이든 “변수는 주소만 들고 있고 실제 객체는 Heap에 있음”이라는 핵심은 같음

## Chapter 05. 접근 제한자와 캡슐화

### 접근 제한자

| 접근 제한자 | 의미 |
| --- | --- |
| `public` | 공개 |
| `private` | 비공개 (클래스 안에서만) |
| `protected` | 상속 관계에서만 공개 |
| `internal` | 같은 어셈블리(패키지) 안에서만 공개 |

함수나 변수 앞에 아무것도 안 붙이면 C#에서는 기본으로 `private`\
그래서 Player의 `healthPoint`, `transformDuration`은 바깥에서 못 건드림\
`attackDamage`만 `public`이라 바깥에서 보임

```csharp
private void SomeFunction()
{
}
```

private 함수는 클래스 안에서만 쓰는 함수를 만들 때 사용

### 캡슐화(Encapsulation)

> 클래스 안에서 만들어진 함수만 가지고 외부와 소통하는 것

Player가 가져야 하는 정보와 기능을 Player 클래스 안에 다 넣어 두고\
외부에서 Player의 정보를 직접 건드리지 못하게 막음\
목적은 **관리 포인트를 줄이기 위해서**

### 두 방식 비교

```csharp
// 1. 외부에서 값에 직접 접근
player.attackDamage += 20;
Debug.Log(player.attackDamage);

// 2. 함수를 통해서 값 변경
player.AddDamage(20);
```

| | 직접 접근 | 함수로 변경 |
| --- | --- | --- |
| 값 바꾸는 위치 | 바꾸는 곳마다 | `AddDamage()` 안 한 곳 |
| 로그 | 바꾸는 곳마다 직접 써야 함 | 함수 안에 이미 들어 있음 |
| 나중에 관리 포인트 | 많아짐 | 줄어듦 |

예를 들어 공격력이 999를 넘으면 안 된다는 규칙이 생기면\
1번 방식은 `attackDamage +=`를 쓴 곳을 다 찾아서 고쳐야 함\
2번 방식은 `AddDamage()` 하나만 고치면 됨

그래서 결론은 **무조건 함수를 통해서 행동해야 함**\
지금 코드는 비교를 보여 주려고 attackDamage를 `public`으로 열어 둔 상태\
진짜 캡슐화하려면 이것도 private으로 막아야 1번 방식 자체가 불가능해질 듯

### API

이렇게 정해진 함수(창구)로만 작업하게 만든 규격을 API(Application Programming Interface)라고 부름

수업 예시는 VARCO\
API 문서를 보면 만들고 싶은 모델의 이름과 프롬프트를 넣으면 완성된 모델링을 줌\
안에서 어떻게 만드는지는 몰라도 정해진 규격대로 넣고 결과만 받음\
이런 걸 API를 통해 작업한다고 함

지난 시간 함수 장점 3번 “이름만 보고 쓸 수 있음 (내부 동작은 몰라도 됨)”이랑 같은 이야기로 보임

## Chapter 06. 함수 오버로딩(Overloading)

```csharp
public void AddDamage()
{
    attackDamage += 90f;
    Debug.Log(attackDamage);
}

public void AddDamage(float _damage)
{
    attackDamage += _damage;
    Debug.Log(attackDamage);
}
```

함수 이름이 같아도 인자 개수가 다르면 구분 가능\
그래서 같은 이름으로 함수를 여러 개 정의할 수 있음

| 호출 | 불리는 함수 | 결과 |
| --- | --- | --- |
| `AddDamage()` | 인자 없는 버전 | +90 (변신할 때) |
| `AddDamage(20)` | float 받는 버전 | +20 |

수업에서는 개수로 설명했는데\
찾아보니 개수가 같아도 인자 자료형이 다르면 오버로딩이 됨 (`AddDamage(int)`와 `AddDamage(float)` 같은 식)\
반대로 출력 타입만 다른 건 구분이 안 됨\
→ 함수 이름 + 인자 구성으로 구분한다고 보면 될 듯

## Chapter 07. 생성자(Constructor)

### 아파트 예제

아파트를 만들 거임\
101동, 102동, 103동, 104동\
동마다 번호만 다르고 설계는 같다고 가정\
기능은 `'나는 **동이다'` 출력하기

### 1차: 동마다 설계도 따로

```csharp
class Apartment102
{
    private string buildingNumber = "102";
    public void Describe()
    {
        Debug.Log($"나는 {buildingNumber}동이다.");
    }
}
// Apartment101, Apartment103 ... 동마다 class 하나씩
```

설계가 같은데 숫자 하나 때문에 class를 동 수만큼 만들어야 함\
지금 파일에서는 주석 처리해 둔 방식

### 2차: 설계도 하나 + SetBuildingNumber

```csharp
public void SetBuildingNumber(string buildingNumber)
{
    this.buildingNumber = buildingNumber;
}
```

Apartment 설계도 하나로 만들고 동 번호를 외부에서 넣어 줌\
근데 `SetBuildingNumber()`를 호출하는 걸 **깜빡하면** 동 정보가 없는 Apartment가 생김

### 3차: 생성자에 넣기

> 생성자(Constructor) : 객체를 생성할 때 무조건 한 번 호출되는 함수

```csharp
접근제한자 클래스이름()
{
    // 생성될 때 수행해야 하는 행동
}
```

```csharp
class Apartment
{
    private string buildingNumber = "";

    public Apartment(string buildingNumber)
    {
        this.buildingNumber = buildingNumber;
    }

    public void Describe()
    {
        Debug.Log($"나는 {buildingNumber}동이다.");
    }
}
```

```csharp
Apartment apartment101 = new Apartment("101");
apartment101.Describe(); // 나는 101동이다.
Apartment apartment102 = new Apartment("102");
apartment102.Describe(); // 나는 102동이다.
```

생성자는 출력 타입을 안 쓰고 이름이 클래스 이름이랑 같음\
`new Apartment("101")`의 괄호 안 값이 생성자 인자로 들어감\
만들 때 번호를 안 넣을 수가 없으니 깜빡하는 문제가 사라짐

**어떤 객체를 생성할 때 무조건 가지고 있어야 되는 정보는 생성자에서 처리하는 게 좋음**

tip으로 들은 말\
사람이 코딩하는 거라 반드시 실수가 나옴\
그래서 사람이 실수를 할 수 없도록 만드는 방향으로 코딩하는 게 좋음

### this

```csharp
this.buildingNumber = buildingNumber;
```

인자 이름이랑 멤버 변수 이름이 둘 다 `buildingNumber`\
`this.`가 붙은 쪽이 **이 객체의 멤버 변수**, 안 붙은 쪽이 들어온 인자\
Chapter 06의 `_damage`처럼 이름을 다르게 짓는 방법도 있고 `this`로 구분하는 방법도 있음

### 기본 생성자와 생성자 오버로딩

```csharp
public Apartment()
{
}
```

생성자를 따로 정의하지 않으면 이런 기본 생성자가 자동으로 만들어짐\
생성자도 함수처럼 인자 개수를 다르게 해서 여러 개 만들 수 있음 → 생성자 오버로딩(Constructor Overloading)

여기서 하나 확인해 본 것\
수업 코드는 `Apartment(string)` 밑에 빈 `Apartment()`도 직접 만들어 둠\
그래서 `new Apartment()`도 그냥 됨

```csharp
Apartment apartment = new Apartment();
apartment.Describe(); // 나는 동이다.
```

콘솔에서 돌려 보니 번호 없이 `나는 동이다.`가 나옴\
3차에서 막으려던 “동 정보 없는 Apartment”가 다시 만들어질 수 있는 상태\
문서 기준으로는 생성자를 하나라도 직접 만들면 기본 생성자는 자동으로 안 생김\
번호를 꼭 받게 하려면 빈 생성자는 안 만드는 쪽이 맞아 보임. [Microsoft 생성자 설명](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/constructors)

## Chapter 08. 종료자

```csharp
~Apartment()
{
    Debug.Log("Apartment 종료자 호출");
}
```

> 종료자 : 객체가 사라질 때 호출되는 함수

생성자 이름 앞에 `~`를 붙인 형태\
생성자가 태어날 때 한 번이면 종료자는 없어질 때 한 번

```csharp
using System; // GC.Collect()를 쓰려고 System namespace를 using

//apartment = null;
//GC.Collect();
```

객체가 언제 사라지는지는 GC(가비지 컬렉터)가 정함\
`apartment = null`로 아무도 가리키지 않게 만들고 `GC.Collect()`로 정리를 시키는 코드\
지금은 주석 처리 상태라 종료자 로그는 아직 직접 확인 안 함

문서 기준으로 종료자는 내가 부르는 게 아니라 GC가 부르고 언제 불릴지도 정해져 있지 않다고 함\
그래서 “반드시 바로 호출된다”보다는 “정리될 때 언젠가 호출된다”에 가까워 보임

`GC.Collect()`가 `System` 안에 있어서 맨 위에 `using System;`을 추가함\
namespace는 이름이 겹치지 않게 묶어 둔 패키지 같은 개념

## 오늘 정리

| 주제 | 기억할 내용 |
| --- | --- |
| OOP | 행동의 주체별로 분류해서 설계 |
| class | 변수(정보) + 함수(기능)를 묶은 사용자 정의 자료형 |
| new | 설계도로 실제 객체를 Heap에 만듦 |
| `.` | 멤버 접근 연산자, `객체.함수()` |
| 멤버 변수 | 객체가 살아 있는 동안 유지 |
| null | 가리키는 객체 없음, 접근하면 NullReferenceException |
| 접근 제한자 | public / private / protected / internal, 기본 private |
| 캡슐화 | 함수로만 소통 → 관리 포인트 줄이기 |
| API | 정해진 창구(규격)로만 작업 |
| 오버로딩 | 같은 이름, 다른 인자 구성 |
| 생성자 | 생성 시 한 번, 필수 정보는 여기서 받기 |
| this | 이 객체의 멤버 변수 |
| 종료자 | `~클래스이름()`, GC가 정리할 때 호출 |

지난 시간에는 Start에 몰려 있던 코드를 기능 단위로 나눴음\
오늘은 그 기능을 다시 **주체(Player, Enemy, Apartment) 단위로** 묶음

관리 포인트 줄이기 → 반복문 → 함수 → 캡슐화로 같은 이야기가 계속 이어지는 중\
생성자 부분은 “기능을 잘 만드는 것”보다 “잘못 쓸 수 없게 만드는 것”이라 방향이 조금 달라 보임\
빈 생성자를 같이 두면 그 의도가 다시 풀릴 수 있다는 것도 확인함
