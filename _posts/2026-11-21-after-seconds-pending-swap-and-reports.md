11월 20일 구현이 들어 있는 최신 코드를 받아 21일 새벽에 이어서 검수함.
교환 예약이 기다리는 동안, 층 이동이 실패했을 때, 관측 보고가 늦게 도착했을 때의 처리를 확인함.

게임 코드에서 수정한 파일은 `ThrowSwapQueue.cs`, `SceneFlow.cs`, `FloorSecurity.cs` 세 개임.
각 문제는 수정 전 코드에서 먼저 재현하고 같은 검사로 수정 결과를 비교함.

## 공간을 기다린 교환이 뒤로 밀리는 문제

유효 대상에 명중하면 3초 뒤 교환을 실행함.
양쪽 도착 공간이 막혀 있으면 예약을 남겨 두고 0.25초 뒤 다시 확인함.
그동안 다른 대상의 예약은 독립적으로 처리돼야 함.

기존 큐는 기다리는 예약을 목록 끝에 다시 넣고, 다음에는 목록 앞부터 꺼냈음.
이때 원래 실행 시각과 목록 순서가 달라질 수 있었음.

| 게임 시각 | 상황 |
| --- | --- |
| 0.0초 | A 명중. 실행 예정은 3.0초 |
| 0.1초 | B 명중. 실행 예정은 3.1초 |
| 3.0초 | A의 공간이 막혀 3.25초부터 다시 시도할 수 있게 됨 |
| 3.5초 | 다음 처리에서 A와 B 모두 실행 가능하지만, 기존 목록은 B → A 순서였음 |

앞선 교환이 플레이어 위치를 바꾸므로 이 순서가 다음 교환의 결과에도 영향을 줄 수 있음.
예약할 때 순번을 저장하고, **지금 실행 가능한 예약 중 실행 시각이 빠른 것부터** 꺼내도록 고침.
시각이 같으면 최초 예약 순번을 따름.

A가 아직 재시도 시각에 도달하지 않았다면 B는 먼저 실행할 수 있음.
예를 들어 3.1초에 처리한다면 A는 계속 기다리고 B가 진행함.
기다리는 한 건이 전체 큐를 막지 않는 기존 규칙은 유지함.

3초 지연, 0.25초 재시도, 대상 재등록에 따른 무효화와 박동 계산도 유지함.

## 승강기가 돌아왔는데 예약은 사라졌음

승강기 이동은 도착할 발판과 머리 공간을 확인하고, 공간이 없으면 플레이어를 태워 원래 층으로 돌아오는 흐름임.

그런데 탑승 직전에 `ClearPending()`을 호출하고 있었음.
도착 검사에 실패해 같은 층으로 돌아와도 기존 교환 예약은 이미 지워진 상태였음.
계단은 성공한 전환 뒤에만 정리하고 있어서 두 경로의 처리 시점도 달랐음.

실제 `Travel` 코루틴을 씬·물리 대역과 함께 실행해 예약 유실을 재현함.
탑승 직전의 취소 호출을 제거하고, 실제로 다음 층으로 넘어갔을 때의 취소는 유지함.

승강기를 타는 동안에는 기존 코드가 `CharacterController`를 꺼 둠.
`PlayerSwap`은 컨트롤러가 꺼져 있으면 예약을 다시 대기시키므로 그 흐름을 사용함.
`PlayerSwap` 자체를 끄면 `OnDisable`에서 예약을 지우기 때문에 컴포넌트를 끄는 방식은 쓰지 않음.

실패 복귀 후 유효한 예약을 이어 가는 것, 정상 도착 후 출발 층 예약을 정리하는 것, 재시도 때 이전 플레이어 구성을 없애는 것을 따로 검사함.

## CCTV는 받을 때와 배정할 때 모두 시각을 봄

관측 기억을 저장하는 함수에는 이미 오래된 보고를 거절하는 조건이 있었음.
하지만 CCTV 호출용 위치는 별도 필드에 저장하고 있었고, 그쪽은 같은 비교 없이 덮어쓰고 있었음.

그래서 최신 B 위치를 알고 있어도 늦게 온 A 위치의 보고로 경비를 보낼 수 있었음.

수신 시점만 고치면 대기 중인 호출이 남음.
A 호출을 받았지만 가용 경비가 없어 기다리는 사이, B에서 더 최신 관측이 들어올 수 있음.
이후 경비가 비었을 때도 A 호출을 그대로 배정하면 같은 문제가 생김.

`ReceiveCameraCall`과 `TryAssignCameraCall` 두 곳에서 호출의 관측 시각을 최신 보고 시각과 비교하도록 고침.
더 오래된 호출은 받거나 새 조사에 배정하지 않음.
같은 시각의 보고를 받는 기준과 기존 12초 만료는 유지함.

## 수정 전후 검사와 실제 Unity 실행

독립 검사에서는 실제 큐 소스 또는 해당 메서드 원문을 C#으로 컴파일함.
대상의 상태, 씬 로드, 물리와 일부 수명주기는 검사에 필요한 대역으로 구성함.

| 독립 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 교환 예약 큐 | 19/22 | 22/22 |
| 층 이동·복귀·재시도 | 7/11 | 11/11 |
| CCTV 보고 수신·배정 | 4/7 | 7/7 |

수정 후 40개 조건이 통과함.
이 결과는 코드의 처리 흐름과 상태를 확인한 범위로 기록함.

이후 Unity **6000.4.0f1**에서 에셋 반입·컴파일을 끝내고 실제 Play 검사를 별도로 실행함.

| 실제 Unity 검사 | 확인한 범위 |
| --- | --- |
| 10개 | 실제 `SwapTarget` 객체와 게임 큐의 재시도 순서·비차단 대기·재등록 무효화·Clear |
| 4개 | 실제 `FloorSecurity` 격리 컴포넌트의 오래된 수신 거절·대기 폐기·동시각 수신·12초 만료 |
| 4개 | B5 경비 로드·누락 스크립트·프레임 진행·배식 완료와 입력 복구 |

Unity에서는 18개 조건이 통과함.
`GameRoot`에서 B5를 불러와 12게임초 동안 진행했고, 식판의 실제 충돌과 첫 위치 교환이 끝난 뒤 조작이 돌아왔음.
경비 24명, 로드된 씬의 누락 스크립트 0개, 검수 도구 실행 중 오류·예외 0개를 확인함.

CCTV 컴포넌트 검사는 경비를 배치하지 않은 격리 검사임.
실제 경비가 관제 호출을 받고 이동하는 경로까지 새로 검수한 결과로 합치지 않음.

## 저장 상태와 다음 확인

검수에 사용한 임시 Editor 스크립트를 정리하고, 에디터 종료 때 비워진 동적 한글 폰트 데이터를 복원함.
게임 씬·프리팹·기존 meta·프로젝트 설정·패키지는 보존함.
오래된 README의 시작 안내도 최신 인수인계로 연결함.

현재 수정과 검수 기록은 로컬에 저장된 상태임.
게임 변경의 커밋·push는 아직 진행하지 않음.

다음에는 실제 B4 도착 공간을 막아 승강기를 왕복시키면서 예약이 유지되는지 확인할 예정임.
CCTV의 실제 경비 배정과 세 코어를 섞은 전체 층 완주도 이어서 확인해야 함.
이번 코드 검사와 B5 시작 검수가 그 플레이를 전부 대신하지는 않음.
