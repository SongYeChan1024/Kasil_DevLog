## Chapter 02. 상속(Inheritance)

### 공통 부분을 Animal로

> 상속 : 공통된 함수나 변수를 하나의 클래스에 묶어 둠

Dog, Cat 말고 클래스를 하나 더 만들어서\
공통된 기능이나 정보를 거기에 모아 둠 → `Animal`\
강아지와 고양이에서 “동물이라면 할 수 있는 것”만 뽑아낸 거라 **추상화**라고 부름

```csharp
class Animal
{
    protected string name = "";
    public string GetName()
    {
        return name;
    }

    public virtual void MakeSound() // 소리를 내는 기능
    {
        Debug.Log(name + "가 소리를 냅니다.");
    }
    public void Move() // 움직이는 기능
    {
        Debug.Log(name + "가 움직입니다.");
    }
    public void Describe() // 자기소개 기능
    {
        Debug.Log("저는 " + name + "입니다.");
    }
    public void Eat() // 먹는 기능
    {
        Debug.Log(name + "가 밥 먹는 중..");
    }
}
```

### 물려받기

```csharp
class Dog : Animal
{
    public Dog()
    {
        name = "강아지";
    }

    public void Chase() // 강아지의 고유 기능
    {
        Debug.Log("누군가를 쫒는다");
    }
}
```

`class 자식 : 부모` 형태\
Dog 안에는 `Move()`, `Describe()`를 안 썼는데 `dog.Move()`가 됨\
Animal이 가진 걸 그대로 물려받은 것

`MonoBehaviour`를 붙이던 `public class Class2 : MonoBehaviour`도 같은 문법이었음\
그동안 계속 상속을 쓰고 있었던 셈

### protected

어제 접근 제한자 표에서 `protected`는 “상속 관계에서만 공개”였음\
오늘 처음 실제로 씀

| name의 접근 제한자 | Dog 생성자에서 `name = "강아지"` | 바깥(Start)에서 `dog.name` |
| --- | --- | --- |
| `private` | 안 됨 | 안 됨 |
| `protected` | 됨 | 안 됨 |
| `public` | 됨 | 됨 |

자식은 건드릴 수 있어야 하고 바깥에서는 못 건드리게 하려면 `protected`\
바깥에서 이름이 필요할 때는 `GetName()` 함수로 받아 감\
어제 캡슐화의 “함수로만 소통”이 그대로 이어짐

이름은 자식 생성자에서 넣음\
어제 배운 “객체를 만들 때 꼭 있어야 하는 정보는 생성자에서”와 같은 방식

### 공통 기능은 한 곳만 고치면 됨

`Eat()`은 Animal에만 추가했음\
그런데 `dog.Eat()`, `cat.Eat()` 둘 다 됨

1차 방식이었으면 Dog, Cat에 각각 넣었어야 함\
관리 포인트가 클래스 개수만큼 → 한 곳으로 줄어듦

### 고유 기능은 각자

| 클래스 | 물려받은 것 | 고유 기능 |
| --- | --- | --- |
| Dog | Move, Describe, Eat, MakeSound | `Chase()` 누군가를 쫒는다 |
| Cat | Move, Describe, Eat, MakeSound | `RunAway()` 가출했다냥 |

공통인 건 부모에, 그 동물만 하는 건 자식에

## Chapter 03. virtual, override, base

### 소리는 동물마다 다름

`MakeSound()`는 공통 기능인데 내용은 동물마다 달라야 함\
상속받은 클래스에서 행동을 바꿀 수 있게 만들어야 함

```csharp
// Animal
public virtual void MakeSound()
{
    Debug.Log(name + "가 소리를 냅니다.");
}

// Dog
public override void MakeSound()
{
    base.MakeSound();
    Debug.Log("멍멍");
}
```

| 키워드 | 붙이는 곳 | 의미 |
| --- | --- | --- |
| `virtual` | 부모 함수 | 가상함수. 자식이 내용을 바꿔도 됨 |
| `override` | 자식 함수 | 함수의 재정의. 함수 오버라이딩(Function Overriding) |
| `base` | 자식 함수 안 | 부모가 원래 가지고 있던 함수를 부름 |

`base.MakeSound()`를 먼저 불러서 부모 것도 한 번 실행하고 그 뒤에 자기 소리를 냄

```text
강아지가 소리를 냅니다.
멍멍
```

콘솔에서 돌려 보니 두 줄이 순서대로 나옴\
`base.MakeSound()` 줄을 빼면 `멍멍`만 나올 것으로 보임 (이건 안 돌려 봄)

### 오버로딩이랑 헷갈림

어제 배운 오버로딩과 이름이 비슷함

| | 오버로딩 (어제) | 오버라이딩 (오늘) |
| --- | --- | --- |
| 어디서 | 같은 클래스 안 | 부모와 자식 사이 |
| 함수 이름 | 같음 | 같음 |
| 인자 | 다름 | 같음 |
| 하는 일 | 같은 이름으로 여러 개 만들기 | 물려받은 함수의 내용 바꾸기 |

`AddDamage()`와 `AddDamage(float)`는 오버로딩\
Animal의 `MakeSound()`와 Dog의 `MakeSound()`는 오버라이딩

## Chapter 04. 다형성

### 부모의 형태로 자식 만들기

```csharp
Dog dog1 = new Dog();
Animal dog2 = new Dog(); // 부모의 형태로 자식을 만들 수 있음
```

변수 자료형은 `Animal`인데 실제로 만든 건 `Dog`

### 그래도 자식 함수가 실행됨

```csharp
dog2.Describe();
dog2.Eat();
dog2.MakeSound();
dog2.Move();
```

```text
저는 강아지입니다.
강아지가 밥 먹는 중..
강아지가 소리를 냅니다.
멍멍
강아지가 움직입니다.
```

Animal 형태로 만들었어도 `멍멍`이 나옴\
부모의 형태로 만들었다고 해도 자식 객체를 만들면 **자식에 재정의된 함수가 실행됨**

### 부모에 없는 함수는 못 씀

```csharp
// dog2.Chase(); // 부모의 형태로 자식을 만들었기 때문에 사용 불가
```

`Chase()`는 Dog에만 있고 Animal에는 없음\
Animal 형태로 들고 있으면 Animal이 아는 함수까지만 부를 수 있음

| | `Dog dog1` | `Animal dog2` |
| --- | --- | --- |
| Describe, Eat, Move | 됨 | 됨 |
| MakeSound | 멍멍 | 멍멍 |
| Chase | 됨 | 안 됨 |

실제 객체는 둘 다 Dog\
변수의 자료형이 “어디까지 부를 수 있는지”를 정하는 것으로 보임

## Chapter 06. SOLID 원칙

수업 주석에 적은 다섯 가지

| | 원칙 | 내용 |
| --- | --- | --- |
| S | Single Responsibility Principle (단일 책임 원칙) | 하나의 클래스는 하나의 책임만 가져야 함 |
| O | Open Closed Principle (개방 폐쇄 원칙) | 클래스는 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 함 |
| L | Liskov Substitution Principle (리스코프 치환 원칙) | 상위 타입의 객체를 하위 타입의 객체로 바꾸어도 프로그램의 동작에는 문제가 없어야 함 |
| I | Interface Segregation Principle (인터페이스 분리 원칙) | 인터페이스는 자신이 사용하지 않는 메서드에 의존하지 않아야 함 |
| D | Dependency Inversion Principle (의존성 역전 원칙) | 상위 모듈은 하위 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 함 |

### 오늘 예제는 O

- 확장: `Duck`
- 변경에 닫혀 있는 녀석: `school`

Duck을 확장하면서 school을 바꾸지 않았음\
새 동물이 생겨도 기존 코드는 그대로 두는 구조

L도 Chapter 04랑 이어지는 걸로 보임\
`Animal` 자리에 `Dog`를 넣었는데 Describe, Eat, Move가 그대로 동작했음

I는 보통 “**쓰는 쪽(클라이언트)** 이 자신이 사용하지 않는 메서드에 의존하지 않아야 한다”로 설명한다고 함\
인터페이스 자체는 아직 안 배워서 그때 다시 볼 부분

S, D는 오늘 코드로 확인한 건 없음. 이름과 뜻만 적어 둠

## Chapter 07. 어제 과제를 상속으로 다시

### 어제 내 풀이는 같은 코드가 두 벌

어제 `Class_20261109.cs`에서는 Player, Enemy를 따로 만들었음\
체력·최대 체력·데미지, 데미지 받기, 힐, 죽기가 양쪽에 거의 똑같이 들어 있음\
Chapter 01의 Dog, Cat이랑 같은 상황

### Entity로 올리기

```csharp
class Entity
{
    protected float currentHp = 0f;
    protected float maxHp = 0f;
    protected float damage = 0f;

    public float GetDamage()
    {
        return damage;
    }

    public virtual void OnDamage(float damage)
    {
        if (currentHp <= 0)
        {
            return;
        }
        currentHp -= damage;
        Debug.Log("PlayerHp: " + currentHp);
        if (currentHp <= 0)
        {
            Die();
        }
    }

    public void Attack(Entity target)
    {
        target.OnDamage(damage);
    }

    protected void Die()
    {
        Debug.Log("플레이어 죽음");
    }

    public void Heal(float healAmount)
    {
        if (currentHp <= 0)
        {
            return;
        }
        currentHp += healAmount;
        if (currentHp > maxHp)
        {
            currentHp = maxHp;
        }
        Debug.Log("Heal - PlayerHp : " + currentHp);
    }

    public bool IsDead()
    {
        return currentHp <= 0;
    }
}
```

Player와 Enemy가 같이 가진 정보·기능을 전부 `Entity`에 올림\
Animal과 같은 역할

### Player, Enemy에 남은 것

```csharp
class Player : Entity
{
    public Player(float currentHp, float maxHp, float damage)
    {
        this.currentHp = currentHp;
        this.maxHp = maxHp;
        this.damage = damage;
    }

    public void DoSkill()
    {
        Debug.Log("Player가 Skill 사용");
    }
}
```

| 클래스 | 직접 가진 것 |
| --- | --- |
| Player | 생성자, `DoSkill()` |
| Enemy | 생성자, `hasRaged`, `Rage()`, `OnDamage()` 재정의 |

Dog의 `Chase()`처럼 그 클래스만 하는 것만 남음

### 처음 값을 넣는 세 가지 방법

파일 주석에 정리된 내용

| 방법 | 단점 |
| --- | --- |
| 1. 멤버 변수의 초기값으로 넣기 | 변경이 쉽지 않음 |
| 2. 값을 세팅하는 함수(Setter) 만들기 | 변수 개수만큼 함수가 필요하고, 만들 때마다 호출해 줘야 함 |
| 3. 생성자 | 1번과 2번의 단점을 모두 해결 |

어제 아파트 예제의 1차 → 2차 → 3차와 같은 순서

### Attack 하나로

```csharp
public void Attack(Entity target)
{
    //데미지를 줄때 필요한 정보
    //1. 누구한테 데미지를 줄건가? -> Enemy
    //2. 얼마만큼 데미지를 줄건가? -> damage
    target.OnDamage(damage);
}
```

주석에는 대상이 Enemy로 적혀 있는데 실제 인자는 `Entity target`\
어제는 `AttackEnemy(Enemy enemy)`, `AttackPlayer(Player player)`를 따로 만들었음\
오늘은 인자가 `Entity`라서 함수 하나로 됨

```csharp
player.Attack(enemy);
enemy.Attack(player);
player.Attack(monster);
```

`school.GoSchool(Animal animal)`과 같은 구조\
Player든 Enemy든 Monster1이든 Entity면 들어감

### Enemy만 OnDamage 재정의

```csharp
public override void OnDamage(float damage)
{
    if (IsDead())
    {
        return;
    }
    currentHp -= damage;

    Debug.Log("EnemyHp: " + currentHp);

    if (currentHp <= 30f && hasRaged == false)
    {
        Rage();
    }

    if (IsDead())
    {
        Die();
    }
}
```

적은 맞을 때 레이지를 확인해야 해서 `OnDamage`를 `override`\
`player.Attack(enemy)`는 Entity의 Attack을 부르는데, 그 안의 `target.OnDamage()`는 Enemy 것이 실행됨\
Chapter 04의 다형성이 과제에서도 그대로 나옴

### IsDead

어제 내 코드는 `isDead`라는 bool을 따로 두고 죽을 때 true로 바꿨음\
오늘 파일은 `return currentHp <= 0;`\
체력에서 바로 계산하니까 따로 관리할 변수가 하나 줄어듦

### 실행 결과

같은 파일을 C# 콘솔(.NET 9.0)로 돌려 봄

```text

PlayerHp: 70
Heal - PlayerHp : 120
Heal - PlayerHp : 95
EnemyHp: 85
EnemyHp: 75
EnemyHp: 65
EnemyHp: 55
EnemyHp: 45
EnemyHp: 35
EnemyHp: 25
Enemy 빡침
EnemyHp: 15
EnemyHp: 5

```

| 순서 | 플레이어 체력 | 적 체력 |
| --- | ---: | ---: |
| 시작 | 100 | 100 |
| 플레이어 공격 | 100 | 90 |
| 적 공격 | 70 | 90 |
| 플레이어 200 회복 | 120 (최대) | 90 |
| 적 5 회복 | 120 | 95 |
| 죽을 때까지 공격 | 120 | 85 → … → 25 (레이지) → 15 → 5 → -5 |

적은 95에서 10씩 10번 맞고 죽음

### 돌려 보고 알게 된 것

| 보인 것 | 이유 |
| --- | --- |
| 적이 회복했는데 `Heal - PlayerHp : 95` | `Heal()`이 Entity로 올라가면서 로그 문구가 Player 기준으로 남음 |
| 적이 죽었는데 `플레이어 죽음` | `Die()`도 같은 이유 |
| 적 체력이 `-5` | 0에서 멈추는 처리가 없음. 어제 내 코드에는 있었음 |

| 적이 10번 맞음 | Start에 넣은 값이 Player 데미지 10, Enemy 최대 체력 120·데미지 30. 과제 문장의 30 / 200 / 10과 다름 |

공통 클래스로 올리면 코드는 줄어드는데\
`"PlayerHp"`처럼 특정 클래스 이름이 박힌 문구는 같이 손봐야 한다는 걸 알게 됨\

## Chapter 08. 다음 과제: 무기 장착

### 문제

```text
Player에게 무기가 생김
player는 sword, arrow, axe 3개의 무기를 장착할 수 있음
sword를 장착하면 데미지가 10 증가
arrow를 장착하면 데미지가 15 증가
axe를 장착하면 데미지가 20 증가
플레이어가 무기를 장착하고 적을 때리는 코드를 작성해 보세요
```

### 일단 짜 둔 코드

```csharp
class Player
{
    private float damage;
    private float baseDamage;
    private float swordDamage = 10f;
    private float arrowDamage = 15f;
    private float axeDamage = 20f;

    public Player(float baseDamage)
    {
        this.baseDamage = baseDamage;
        this.damage = baseDamage;
    }

    public void EquipWeapon(string weapon)
    {
        if (weapon == "sword")
        {
            damage = baseDamage + swordDamage;
            Debug.Log("플레이어가 검을 장착했습니다. 데미지 증가: " + swordDamage);
        }
        else if (weapon == "arrow")
        {
            damage = baseDamage + arrowDamage;
            Debug.Log("플레이어가 활을 장착했습니다. 데미지 증가: " + arrowDamage);
        }
        else if (weapon == "axe")
        {
            damage = baseDamage + axeDamage;
            Debug.Log("플레이어가 도끼를 장착했습니다. 데미지 증가: " + axeDamage);
        }
        else
        {
            Debug.Log("알 수 없는 무기입니다.");
        }
    }

    public void Attack(Enemy enemy)
    {
        Debug.Log($"플레이어가 {damage}의 데미지를 입혔습니다.");
        enemy.OnDamage(damage);
    }
}
```

`baseDamage`를 따로 둔 이유\
무기를 바꿀 때 `damage += 10`으로 하면 바꿀 때마다 계속 쌓임\
`damage = baseDamage + 무기 데미지`로 다시 계산하면 지금 든 무기만 반영됨

### 결과 확인

```text
플레이어가 10의 데미지를 입혔습니다.
에너미가 10의 데미지를 입었습니다. 현재 HP: 75
플레이어가 검을 장착했습니다. 데미지 증가: 10
플레이어가 20의 데미지를 입혔습니다.
에너미가 20의 데미지를 입었습니다. 현재 HP: 55
플레이어가 활을 장착했습니다. 데미지 증가: 15
플레이어가 25의 데미지를 입혔습니다.
에너미가 25의 데미지를 입었습니다. 현재 HP: 30
플레이어가 도끼를 장착했습니다. 데미지 증가: 20
플레이어가 30의 데미지를 입혔습니다.
에너미가 30의 데미지를 입었습니다. 현재 HP: 0
에너미가 죽었습니다.
```

| 무기 | 데미지 | 적 체력 |
| --- | ---: | ---: |
| 없음 | 10 | 85 → 75 |
| sword | 20 | 55 |
| arrow | 25 | 30 |
| axe | 30 | 0 |

10 + 20 + 25 + 30 = 85라서 적 체력 85가 마지막에 딱 0이 됨

### 걸리는 부분

- 무기를 `"sword"` 같은 문자열로 받음. 오타를 내면 컴파일은 되고 실행해서야 `알 수 없는 무기입니다.`가 나옴
- 무기를 하나 추가하려면 Player의 `EquipWeapon()`에 `else if`를 더 넣어야 함

두 번째가 오늘 배운 O(개방 폐쇄 원칙)랑 반대 방향으로 보임\
Duck은 school을 안 고치고 추가했는데, 여기서는 무기를 추가할 때마다 Player를 고쳐야 함

`Weapon`이라는 부모를 두고 Sword, Arrow, Axe가 물려받게 하면\
Player는 `EquipWeapon(Weapon weapon)` 하나로 받을 수 있을 듯\
아직 그렇게 바꿔 보지는 않음

이번 파일은 Player, Enemy를 `Class_20261111` 클래스 **안에** 넣었음\
그러면 이름이 `Class_20261111.Player`가 돼서 다른 파일의 Player와 안 겹침\
어제는 namespace로 감쌌고 이번에는 클래스 안에 넣은 방식

어제는 정보와 기능을 **주체 단위로** 묶었음\
오늘은 그 주체들 사이에서 **겹치는 부분을 위로** 올림

관리 포인트 줄이기 → 반복문 → 함수 → 캡슐화 → 상속으로 같은 이야기가 또 이어짐\
함수는 같은 코드를 한 곳에, 상속은 같은 함수를 한 클래스에 모으는 것

다형성은 `Animal dog2 = new Dog();` 한 줄만 보면 어디에 쓰는지 잘 안 보임\

받는 쪽이 부모 형태로만 알고 있으면 자식이 늘어나도 받는 쪽은 안 고쳐도 됨

과제를 Entity로 올린 파일은 돌려 보니 로그가 전부 Player 기준으로 찍혔음\
공통으로 올릴 때는 코드뿐 아니라 그 안의 문구까지 공통으로 맞는지 봐야 한다는 것도 같이 확인함
