# 품질 기준과 검증 유지

작성자: 송예찬

요청된 범위의 기존 명세·테스트·검증 스크립트·CI·예외 기록을 먼저 읽습니다. 품질 기준 설정·변경 또는 검사 완화 검토에 사용하며, 모든 작업에 새 품질 도구나 전수 검사를 도입하지 않습니다.

1. 명세에 적힌 기준, 현재 측정값, 실행하지 못한 검사를 구분합니다. 커버리지·성능 수치가 없으면 측정 전 숫자를 만들거나 외부 예시 수치를 새 의무로 채택하지 않습니다.
2. 기준을 새로 정하거나 고칠 때에는 해당 프로젝트의 기존 품질 문서에 아래 관계를 기록합니다. 기준 문서가 없고 지속 관리가 필요할 때만 프로젝트 관례에 맞춰 한 문서를 만듭니다.

| 항목 | 기록할 내용 |
| --- | --- |
| 기준·근거 | 보호할 동작과 현행 요구사항 |
| 검사·실패 조건 | 실제 명령/수동 절차와 어떤 결과가 실패인가 |
| 실행 시점 | 편집 후, 작업 완료 전, CI 중 비용에 맞는 위치 |
| 상태 | 정의됨, 실행 확인됨, 자동 적용됨, 미검증 중 실제 상태 |
| 예외 | 사유·영향·대체 검증·해제 조건과 필요한 합의 |

3. 가벼운 문법·정적 검사는 빠른 피드백에, 관련 테스트는 작업 완료 전에, 느린 통합 검사는 적절한 CI나 별도 검증에 둡니다. 같은 검사를 이유 없이 반복하지 않습니다. Unity 컴파일·참조·플레이, 문서 링크, 블로그 기능 검사는 각 변경의 책임에 맞춰 선택합니다.
4. 새 자동 차단을 만들거나 바꾼 경우 안전한 임시 자료로 정상 입력 통과, 위반 입력 실패, 검사 실행 오류 실패를 확인합니다. 보고서 생성·설정 파일 존재만으로 기준이 강제된다고 말하지 않습니다. 실제 검사기가 없는 의미 판단은 수동 검토로 표시합니다.
5. 이번 diff에서 테스트 삭제·skip/ignore, 단언 축소, 빈 구현·예외 삼키기, 검사 비활성화, 임계값 완화를 살핍니다. 통과를 목적으로 기준을 약화하지 않습니다. 요구사항 변경으로 낡은 검사를 고치는 경우 근거·영향·대체 검증을 남기고 팀 합의가 필요한 기준은 합의 후 변경합니다. 정당한 삭제나 예외를 패턴만으로 일괄 차단하지 않습니다.
6. 검사 실패는 제품 오류, 검사 자체 오류, 기존 실패, 환경/의존성 문제로 구분해 재현 근거를 남깁니다. 기존 실패를 숨기거나 이번 변경의 실패로 섞지 않습니다. 수정할 수 없는 환경 제한은 미검증으로 보고하고 통과로 바꾸지 않습니다.

새 스캐너·테스트 프레임워크 설치와 CI 수정은 실제 요청 범위에서만 수행합니다. 현재 공통 훅의 설치 해시·문법·관련 검사와 이 스킬의 판단 기준은 구분합니다. 이 문서를 읽었다는 사실만으로 테스트 삭제나 임계값 변경을 자동 차단하는 기능이 생기지 않습니다.
