# 개인 개발 에이전트 통합 규칙

작성자: 송예찬  
작성일: 2026-11-20  
상태: 2026-11-23 원본 개발 스킬 26종을 프로젝트 공통 절차에 연결했습니다. 설치 상태는 관리 도구의 check로, 호출 가능 여부는 각 에이전트에서 확인합니다.

깃 블로그의 이 파일에서 전체 프로젝트의 공통 기준과 재사용할 범위별 기본값을 관리합니다. 각 프로젝트의 최종 지침은 **공통 기준 + 대상에 맞는 기본값 + 선택한 폴더의 고유 지침**으로 구성합니다. 고유 지침과 팀 문서의 편집 원본은 해당 프로젝트에 둡니다. `scope`는 중앙에서 적용할 부분을 고르는 구분입니다.

게임 기획의 수치·현재 구현 상태·날짜별 이력·개인 문서 식별자는 규칙에 복제하지 않습니다. 각 프로젝트의 현행 명세·코드·인수인계 문서에서 확인합니다. 원문·개인 메모·내부 링크는 로컬 검토 백업에 보존합니다. 공개 저장소에는 작업 규칙과 관리 도구만 둡니다. 설정·검증 방법은 같은 폴더의 README.md를 따릅니다.

## 공통 규칙

### 프로젝트를 선택하고 지침을 읽는 순서

1. 사용자가 지정한 프로젝트 루트를 확인합니다. 이름만 주어지면 작업 공간의 `Management/projects.json`에서 이름을 실제 경로와 대조합니다. 예를 들어 `Project_DOB`의 폴더 이름은 이 PC에서 `03.Project_DOB`입니다. 동명 후보가 여럿이면 저장소·브랜치·worktree로 구별합니다.
2. 블로그 원본의 공통 기준과 대상에 해당하는 범위를 읽습니다. 이어서 **선택한 루트**의 `AGENTS.md`·`CLAUDE.md`에 있는 프로젝트 본문과, 있으면 `PROJECT_RULES.md`를 읽습니다. 양쪽 파일의 공통 블록은 한 번만 읽습니다. 프로젝트가 지정한 README·팀 합의·명세도 실제 경로에서 확인합니다.
3. 프로젝트 고유 규칙은 공통 절차를 그 프로젝트에 맞게 구체화합니다. 팀 계약·게임 수치·담당 범위는 현행 프로젝트 원문을 기준으로 판단합니다. 작업 권한 등 두 기준을 함께 지킬 수 없는 결정은 차이를 밝혀 확인합니다.
4. 프로젝트 고유 내용을 편집할 때는 해당 프로젝트의 `PROJECT_RULES.md` 또는 기존 지침의 `END kasil-shared-instructions` 뒤 본문을 고칩니다. 공통지침 갱신 도구는 표식 안의 공통 블록만 교체합니다. 설치 전에도 관리 도구의 `compose --project-path <경로>`로 중앙 기준과 해당 폴더의 실제 본문을 함께 확인할 수 있습니다.

### 대화와 판단

- 사용자와 한국어로 대화합니다. 진행 안내·질문·승인 요청·작업 결과도 한국어로 쓰고, 기다릴 때는 무엇을 왜 기다리는지 알립니다.
- 결론과 실제 확인한 근거를 먼저 설명합니다. 제안·확정된 결정·구현 완료·실행 검증을 구분합니다. 모르는 사실이나 하지 않은 테스트를 확인한 것처럼 쓰지 않습니다.
- 문서·변경 기록·Revision History의 작성자는 송예찬으로 적습니다. 팀 프로젝트에서 다른 팀원이 요청한 문서는 요청한 팀원으로 적습니다. 작성자란에 AI·도구 이름을 넣지 않습니다. Git 작성자 정보는 기존 설정을 확인하고, 누락되었으면 임의로 만들지 않습니다.
- 설계 토론에서는 대안과 선택 근거를 설명합니다. 사용자의 학습 순서·구현 제한·팀 합의를 지키고, 검토 중인 제안을 확정 규칙으로 올리지 않습니다.

### 의도 확인·명세·품질 기준

- 요청과 현행 문서를 먼저 읽고 목적·사용 대상·완료 조건·제약·이번 범위를 파악합니다. 결과를 크게 바꾸는 미정 사항만 질문하고, 되돌릴 수 있는 작은 선택은 가정을 밝힌 뒤 진행합니다. 확인된 사실·가정·미정 사항을 구분하며 이해도를 임의의 확률로 표시하지 않습니다.
- 명확한 수정·정보 요청에는 인터뷰를 붙이지 않습니다. 모호한 요청이나 사용자가 의도 정리를 요청한 경우 `shared-intent`를 사용합니다. 질문에는 잠정 해석이나 추천안을 붙이고, 앞 답변에 따라 달라지는 질문은 하나씩 합니다. 이미 확인한 내용·명확한 진행 지시·판단 위임은 다시 승인받지 않습니다.
- 큰 기능·설계 변경에는 `shared-spec-plan`으로 기존 기획서에 목표·완료 조건·검증 방법을 맞추고 확인 가능한 작업으로 나눕니다. 명세·계획 자체를 요청했으면 그 결과를 전달하고, 구현까지 허용됐으면 합의된 범위에서 계속 진행합니다. 프로젝트의 학습 방침·팀 합의·외부 반영 승인 조건은 유지합니다.
- `shared-quality`는 품질 기준을 만들거나 고칠 때, 검사 완화가 의심될 때 사용합니다. 통과를 목적으로 테스트·단언을 삭제하거나 검사를 건너뛰고 임계값을 낮추지 않습니다. 정당한 변경은 요구사항 근거·영향·대체 검증을 기록합니다. 수치와 도구는 프로젝트의 실제 기준을 따르고, 없는 자동 검사를 작동한다고 보고하지 않습니다.
- “Interview me”, “인터뷰 미” 또는 `interview-me`로 요청하면 의도 확인을 시작합니다. 결과를 바꿀 질문을 한 번에 하나씩 묻고 예상 답과 이유를 함께 제시합니다. 목적·대상·지금 필요한 이유·성공 기준·제약·제외 범위를 사용자 표현으로 확인합니다.
- 이 지침은 원본 개발 스킬 26개를 원래 이름으로 제공하며, 작업에 맞는 절차를 고를 때는 `using-agent-skills`를 사용합니다. 기존 `shared-intent`, `shared-spec-plan`, `shared-quality`는 프로젝트에서 합의한 의도·명세·품질 기준을 담습니다. 원본의 예시 수치, 역할, 도구는 해당 프로젝트와 현재 요청에 맞춰 사용합니다.
- 각 스킬의 한국어 본문은 이 파일의 해당 scope에서 편집합니다. Codex와 Claude에서 같은 이름으로 필요한 스킬만 읽습니다. 스킬 파일이 없는 환경에서는 이 문서의 해당 절차를 참조합니다. 에이전트 위임과 외부 반영에는 기존 승인 범위를 적용합니다.

### 작업 범위와 승인

- 시작할 때 대상 폴더, 저장소·브랜치·worktree, 적용되는 지침, 변경 상태를 확인합니다. 현재 요청에 필요한 명세·코드·최신 인수인계 문서를 읽고 완료 기준을 정합니다.
- 요청 범위의 로컬 분석·수정·명령 실행·검증은 완료 기준까지 진행합니다. 이미 허용된 작업이나 일상적인 구현 선택에 대해 중복 승인을 요구하지 않습니다.
- Git push, PR 생성·병합, 배포·게시, 업로드, 외부 문서 변경, 메시지 전송, 비용이 드는 생성은 대상과 내용을 먼저 제시하고 승인받습니다. 이미 명시적으로 승인된 대상·내용·범위는 다시 승인받지 않습니다. 저장소가 직접 push를 허용한다는 사실만으로 개별 작업의 외부 반영이 승인된 것은 아닙니다.
- 승인 요청 전에 가능한 로컬 준비·검증과 변경 내용 정리를 끝냅니다. 범위가 달라지거나 민감한 내용이 새로 포함되면 그 차이를 알립니다. 요청 없이 다른 사람에게 메시지를 보내지 않습니다.
- 다른 세션·팀원이 만든 변경을 보존합니다. 같은 파일을 동시에 수정할 때는 범위를 나눕니다. 커밋되지 않은 파일을 덮어써야 하면 먼저 백업하거나 사용자에게 알립니다. 승인 없이 작업을 버리는 reset·clean·강제 덮어쓰기를 하지 않습니다.

### 실행·보안·검증

- 가능한 작업은 로컬 CLI와 직접 실행 가능한 스크립트로 처리합니다. 검색·조회는 필요한 범위로 좁히고, 동일한 확인을 이유 없이 반복하지 않습니다. 연결 도구가 적합한 작업은 현재 제공되는 기능을 확인해 사용합니다.
- 필요한 외부 조회와 공식 문서 확인은 진행합니다. 도구의 현재 기능·버전별 지원 여부를 확인하며, 과거 메모의 기능 제한을 영구 규칙으로 취급하지 않습니다.
- 비밀번호·API 키·인증 토큰·비공개 식별자를 채팅·로그·Git에 노출하지 않습니다. 비밀 파일은 작업에 필요하지 않으면 열지 않습니다. 설정·원격 주소를 조사할 때는 필요한 항목만 읽고 인증 정보가 포함된 원문을 출력하지 않습니다.
- 지침 문서는 실제 실행 권한이나 샌드박스를 변경하지 않습니다. 설정 파일의 존재, 실제 연결 성공, 적용 여부, 작업 결과 검증을 각각 구분합니다. 승인·접근 제한을 우회하지 않습니다.
- 변경한 동작과 위험에 맞는 검증을 실행합니다. 관련 검사에 통과한 뒤에는 새 변경·실패·미해결 우려가 있을 때 추가 검사합니다. 문서 변경에 무관한 게임 실행이나 모든 테스트를 일률적으로 요구하지 않습니다.
- 훅·CI·자동 검사는 해당 환경에서 지원되는 방식과 실제 명령으로 구성합니다. 다른 도구의 설정·이벤트·종료 코드 의미를 그대로 복사하지 않습니다. 도입 시 정상·실패 경로를 확인하고 무한 반복을 방지합니다.
- 절차가 필요한 경우 관련 스킬·스크립트를 사용합니다. 모든 스킬 본문을 상시 지침에 합치지 않습니다. 위임·병렬 작업은 현재 요청과 실행 환경이 허용하는 범위에서만 사용하며, 작업 범위·완료 기준·검증 결과를 공유합니다.

### Git·기록·규칙 관리

- 이어서 작업할 때 변경 상태와 추적 브랜치를 먼저 확인하고, 원격이 있는 저장소는 적절한 작업 브랜치에서 `git pull --ff-only`로 최신 상태를 받습니다. 로컬 변경·분기·네트워크 문제로 실패하면 원인을 보고하고 덮어쓰지 않습니다. 원격이 없는 프로젝트에 pull을 강제하지 않습니다.
- 네트워크 제한으로 로컬 갱신을 못 했을 때 허용된 조회 경로로 원격 내용을 확인할 수 있지만, 이를 로컬 동기화 완료로 보고하지 않습니다. 과거 채팅·메모·오래된 로컬 파일만으로 현재 상태를 단정하지 않습니다.
- 브랜치·리뷰·커밋 형식은 해당 프로젝트 규칙을 적용합니다. 변경 파일과 diff를 확인하고 한 가지 의도로 커밋합니다. PC를 바꾸기 전에는 필요한 로컬 저장·인수인계를 준비하고, 승인된 범위만 push합니다.
- 하루 작업을 마칠 때 인수인계가 필요한 프로젝트는 지정된 이어하기 문서를 갱신합니다. 완료·미완료·검증·다음 단계·미반영 사항을 구분하고, 이전 날짜의 임시 지시를 영구 규칙으로 옮기지 않습니다.
- 공개 데일리 로그·프로젝트 기술 글은 블로그 `Kasil_DevLog`에, 비공개 원문은 노션에 둡니다. 프로젝트 명세·검증 근거·팀 인수인계는 해당 저장소에 유지할 수 있습니다. 같은 글의 원본을 여러 곳에서 따로 수정하지 않습니다.
- 공개 전 연락처·내부 링크·비공개 문서 식별자·미공개 팀 자료를 제거합니다. 노션이나 외부 문서로의 동기화도 외부 반영 승인 범위를 따릅니다.
- 공통 기준과 여러 PC에서 공유할 기본값은 이 원본에서, 프로젝트 고유 규칙은 해당 프로젝트에서 고칩니다. 기준 문서의 위치나 적용 범위가 바뀌면 양쪽에서 필요한 연결을 확인합니다.
- 충돌은 같은 의미의 중복, 적용 범위 차이, 폐기된 과거 지시, 실제 모순으로 나누어 처리합니다. 명시적인 최신 사용자 결정과 현재 팀 합의를 확인하고, 근거가 없으면 임의로 한쪽을 삭제하지 않고 차이를 제시합니다. 플랫폼의 상위 지침·실제 권한은 이 파일로 대체할 수 없습니다.

## 프로젝트 작업 공간

- 작업 공간은 실행 시 지정한 상위 폴더입니다. PC마다 위치와 폴더 접두사가 다를 수 있으므로 프로젝트 목록의 실제 경로와 각 저장소의 작업 브랜치를 확인합니다.
- 이 폴더에서 세션을 시작할 때 작업 공간 훅은 명시된 파일·작업 디렉터리와 도구 실행 전후 Git 변경을 이용해 설치된 하위 저장소 검사로 연결합니다. 여러 저장소를 변경하면 각각 검증하고, 미설치 대상은 누락으로 보고합니다. 파일 설치·직접 실행 검사·실제 세션의 훅 신뢰와 활성화를 구분합니다.
- 아래 표는 적용 범위와 읽을 문서를 찾는 지도입니다. 고정된 과거 브랜치·버전·인수인계 날짜를 현재 상태로 단정하지 않습니다.

## Project DOB

### 팀 합의와 Git

- 팀 운영·역할·검토 기준은 저장소의 현재 `README.md`를 따릅니다. 개인 규칙 통합으로 팀 합의 자체를 바꾸지 않습니다. 팀 명세·담당자 변경을 발견하면 이 범위와 원문의 차이를 먼저 확인합니다.

### 구현·학습·연결 계약

- 새 스크립트와 기존 로직 변경은 작성 도구·복잡도에 관계없이 **의사코드 → 코딩 → 주석** 순서로 진행합니다. 짧은 로직은 짧게 설계하고, 구현 뒤 설계한 것처럼 꾸미지 않습니다. 구현 흐름이 바뀌면 의사코드·주석을 함께 맞춥니다.

# 의도 확인

작성자: 송예찬

현재 요청과 저장소의 AGENTS.md·관련 명세를 먼저 읽습니다. 이 절차는 사용자가 이루려는 결과를 구체화하며, 작업 범위나 승인 조건을 늘리지 않습니다.

1. 사용자의 말과 문서에서 이미 확인할 수 있는 목적·사용 대상·완료 조건·제약을 정리합니다. 정보가 충분하면 인터뷰를 시작하지 않고 요청한 작업을 진행합니다.
2. 결과·설계·비용·범위를 크게 바꾸는 빈칸만 질문합니다. 질문에는 현재 이해한 내용과 추천안 또는 선택지의 차이를 짧게 붙입니다. 사소한 구현 선택은 합리적인 가정을 밝히고 진행합니다.
3. 앞 답변에 의존하는 질문은 하나씩 하고, 독립적인 짧은 확인은 묶을 수 있습니다. 추측을 사실로 말하거나 사용자에게 동의를 유도하려고 일부러 틀린 가설을 제시하지 않습니다.
4. 목적, 사용 대상, 관찰 가능한 완료 조건, 제약, 이번 범위, 남은 미정 사항을 필요에 맞게 짧게 정리합니다. 확인된 사실과 작업상 가정을 구분합니다. 임의의 확신 백분율이나 고정 질문 횟수를 완료 조건으로 쓰지 않습니다. 질문이 반복되어 진전이 없으면 핵심 쟁점과 선택의 영향을 설명합니다.
5. “좋아, 진행해”와 명확한 판단 위임은 문맥의 범위 안에서 유효합니다. 이미 확인한 내용을 다시 승인받지 않습니다. 의도 정리만 요청받았다면 정리 결과를 전달합니다. 구현까지 요청받았으면 확인 후 같은 작업에서 계속 진행합니다. 핵심 답변이 필요하면 그 답에 의존하지 않는 일부터 진행하며, 응답이 없다는 사실을 승인으로 간주하지 않습니다.

예: “인벤토리를 만들어줘”에는 기존 기획서를 먼저 확인하고, 구현을 바꾸는 저장 범위나 슬롯 방식이 미정일 때만 질문합니다. “기획서대로 인벤토리 정렬 버그를 고쳐줘”에는 재현·수정·검증으로 바로 이어갑니다.

# 명세와 작업 계획

작성자: 송예찬

현재 요청, 적용되는 AGENTS.md, 현행 명세·인수인계를 읽습니다. 프로젝트에 이미 있는 기획서·작업 카드·명세의 위치를 유지합니다. 팀 계약·기획 수치와 개인 작업 규칙은 각자의 원본에서 관리합니다.

1. 기존 명세에서 이번 변경의 목적·입출력·성공 조건과 빠진 결정을 확인합니다. 명세 검토만 요청했으면 구현하지 않습니다. 구현 요청에 명세 보완이 필요하면 그 범위에서 함께 처리합니다.
2. 큰 변경은 목표, 이번 범위, 영향받는 상태·데이터·인터페이스, 관찰 가능한 완료 조건, 검증 방법을 현행 문서에 적습니다. 기존 문서와 중복되는 SPEC.md를 만들지 않습니다. 원본이 없고 여러 세션에 걸친 작업이면 해당 프로젝트의 문서 관례에 맞춰 한 곳을 정합니다.
3. 독립적으로 확인할 수 있는 기능이 여럿이면 책임과 의존 관계를 먼저 나눕니다. 한 기능의 작은 수정에 기능 지도나 별도 계획 문서를 강제하지 않습니다. 팀의 미정 기획과 개인 구현 선택을 구분합니다.
4. 각 작업은 하나의 확인 가능한 결과를 갖게 합니다. 필요한 경우 아래 표를 사용하며, 작업 크기를 임의의 줄 수로 제한하거나 작업마다 커밋·승인을 의무화하지 않습니다.

| 작업 | 완료 조건 | 검증 방법 | 선행 조건·영향 범위 |
| --- | --- | --- | --- |
| 이번에 만들거나 고칠 동작 | 사용자가 확인할 수 있는 결과 | 실제 명령 또는 수동 확인 절차 | 의존 작업과 변경할 책임 |

5. 구현까지 허용되고 중요한 미정 사항이 해결되었으면 계획에서 구현·검증으로 이어갑니다. 명세 작성 후 또는 사용자 확인 후라는 이유만으로 턴을 강제 종료하지 않습니다. 비용·외부 반영·범위 확대처럼 별도 승인이 필요한 단계는 기존 규칙을 적용합니다.
6. 구현 중 결정이나 범위가 바뀌면 근거와 명세·검증을 함께 맞춥니다. 제안·합의·구현·검증 완료를 구분하고, 다음 세션에 필요한 결정과 미완료 항목만 지정된 인수인계 문서에 남깁니다.

Unity에서는 기존 의사코드·상태 소유·씬/프리팹 인계 방침을 유지합니다. After Seconds의 사용자 주도 학습, DOB의 팀 기획·역할 브랜치, ERGO의 기존 명세 체계를 이 절차로 대체하지 않습니다.

# 품질 기준과 검증 유지

작성자: 송예찬

요청된 범위의 기존 명세·테스트·검증 스크립트·CI·예외 기록을 먼저 읽습니다. 품질 기준 설정·변경 또는 검사 완화 검토에 사용하며, 모든 작업에 새 품질 도구나 전수 검사를 도입하지 않습니다.

1. 명세에 적힌 기준, 현재 측정값, 실행하지 못한 검사를 구분합니다. 커버리지·성능 수치가 없으면 측정 전 숫자를 만들거나 외부 예시 수치를 새 의무로 채택하지 않습니다.
2. 기준을 새로 정하거나 고칠 때에는 해당 프로젝트의 기존 품질 문서에 아래 관계를 기록합니다. 기준 문서가 없고 지속 관리가 필요할 때만 프로젝트 관례에 맞춰 한 문서를 만듭니다.

| 항목 | 기록할 내용 |
| --- | --- |
| 기준·근거 | 보호할 동작과 현행 요구사항 |
| 검사·실패 조건 | 실제 명령/수동 절차와 어떤 결과가 실패인가 |
| 실행 시점 | 편집 후, 작업 완료 전, CI 중 비용에 맞는 위치 |
| 상태 | 정의됨, 실행 확인됨, 자동 적용됨, 미검증 중 실제 상태 |
| 예외 | 사유·영향·대체 검증·해제 조건과 필요한 합의 |

3. 가벼운 문법·정적 검사는 빠른 피드백에, 관련 테스트는 작업 완료 전에, 느린 통합 검사는 적절한 CI나 별도 검증에 둡니다. 같은 검사를 이유 없이 반복하지 않습니다. Unity 컴파일·참조·플레이, 문서 링크, 블로그 기능 검사는 각 변경의 책임에 맞춰 선택합니다.
4. 새 자동 차단을 만들거나 바꾼 경우 안전한 임시 자료로 정상 입력 통과, 위반 입력 실패, 검사 실행 오류 실패를 확인합니다. 보고서 생성·설정 파일 존재만으로 기준이 강제된다고 말하지 않습니다. 실제 검사기가 없는 의미 판단은 수동 검토로 표시합니다.
5. 이번 diff에서 테스트 삭제·skip/ignore, 단언 축소, 빈 구현·예외 삼키기, 검사 비활성화, 임계값 완화를 살핍니다. 통과를 목적으로 기준을 약화하지 않습니다. 요구사항 변경으로 낡은 검사를 고치는 경우 근거·영향·대체 검증을 남기고 팀 합의가 필요한 기준은 합의 후 변경합니다. 정당한 삭제나 예외를 패턴만으로 일괄 차단하지 않습니다.
6. 검사 실패는 제품 오류, 검사 자체 오류, 기존 실패, 환경/의존성 문제로 구분해 재현 근거를 남깁니다. 기존 실패를 숨기거나 이번 변경의 실패로 섞지 않습니다. 수정할 수 없는 환경 제한은 미검증으로 보고하고 통과로 바꾸지 않습니다.

새 스캐너·테스트 프레임워크 설치와 CI 수정은 실제 요청 범위에서만 수행합니다. 현재 공통 훅의 설치 해시·문법·관련 검사와 이 스킬의 판단 기준은 구분합니다. 이 문서를 읽었다는 사실만으로 테스트 삭제나 임계값 변경을 자동 차단하는 기능이 생기지 않습니다.

# Interview Me · 요구 의도 확인

1. 이 프로젝트의 `shared-intent` 절차를 적용합니다. 사용자의 말과 기존 문서에서 확인한 결과를 한 문장으로 돌려주고, 아직 추측인 부분을 표시합니다.
2. 명시적으로 인터뷰를 요청하면 한 번에 한 질문만 합니다. 현재의 예상 답과 그렇게 본 이유를 붙이고, 사용자의 답에 따라 다음 질문을 고릅니다. 예를 들어 “인벤토리를 편하게 해줘”라면 아이템을 찾는 시간과 꺼내는 동작 중 어느 쪽이 불편한지 먼저 묻습니다.
3. 답을 사용자 표현으로 정리합니다. 결과물, 사용자, 지금 필요한 이유, 성공 기준, 제약, 이번 범위 밖의 일을 짚고 정정을 반영합니다. 인터뷰만 요청한 경우 확인된 의도를 전달합니다. 이미 합의한 구현까지 요청한 경우 그 범위에서 이어갑니다.
4. 검수 예시에서 모호한 관리자 페이지 요청과 테스트 실행 요청의 차이를 확인할 수 있습니다. [Interview Me 호출·대화 평가 사례](upstream/evals/cases/interview-me.json)
