상태: 2026-11-20 사용자 요청으로 채택한 통합 규칙. 실제 설치·활성화 상태는 관리 도구의 check와 각 에이전트에서 확인합니다.

이 파일은 Codex와 Claude Code에 적용할 개인 작업 규칙의 단일 편집 원본입니다. 공통 규칙과 해당 작업의 적용 범위만 읽습니다. 다른 프로젝트의 규칙을 현재 프로젝트에 적용하지 않습니다. `scope` 구간은 같은 원본에서 도구별 진입 파일을 만들기 위한 구분입니다. 생성 파일은 직접 편집하지 않습니다.

게임 기획의 수치·현재 구현 상태·날짜별 이력·개인 문서 식별자는 규칙에 복제하지 않습니다. 각 프로젝트의 현행 명세·코드·인수인계 문서에서 확인합니다. 원문·개인 메모·내부 링크는 로컬 검토 백업에 보존합니다. 공개 저장소에는 작업 규칙과 관리 도구만 둡니다. 설정·검증 방법은 같은 폴더의 README.md를 따릅니다.

## 공통 규칙

### 대화와 판단

- 사용자와 한국어로 대화합니다. 진행 안내·질문·승인 요청·작업 결과도 한국어로 쓰고, 기다릴 때는 무엇을 왜 기다리는지 알립니다.
- 결론과 실제 확인한 근거를 먼저 설명합니다. 제안·확정된 결정·구현 완료·실행 검증을 구분합니다. 모르는 사실이나 하지 않은 테스트를 확인한 것처럼 쓰지 않습니다.
- 문서·변경 기록·Revision History의 작성자는 송예찬으로 적습니다. 팀 프로젝트에서 다른 팀원이 요청한 문서는 요청한 팀원으로 적습니다. 작성자란에 AI·도구 이름을 넣지 않습니다. Git 작성자 정보는 기존 설정을 확인하고, 누락되었으면 임의로 만들지 않습니다.
- 설계 토론에서는 대안과 선택 근거를 설명합니다. 사용자의 학습 순서·구현 제한·팀 합의를 지키고, 검토 중인 제안을 확정 규칙으로 올리지 않습니다.

### 작업 범위와 승인

- 시작할 때 대상 폴더, 저장소·브랜치·worktree, 적용되는 지침, 변경 상태를 확인합니다. 현재 요청에 필요한 명세·코드·최신 인수인계 문서를 읽고 완료 기준을 정합니다.
- 요청 범위의 로컬 분석·수정·명령 실행·검증은 완료 기준까지 진행합니다. 이미 허용된 작업이나 일상적인 구현 선택에 대해 중복 승인을 요구하지 않습니다.
- Git push, PR 생성·병합, 배포·게시, 업로드, 외부 문서 변경, 메시지 전송, 비용이 드는 생성은 대상과 내용을 먼저 제시하고 승인받습니다. 이미 명시적으로 승인된 대상·내용·범위는 다시 승인받지 않습니다. 저장소가 직접 push를 허용한다는 사실만으로 개별 작업의 외부 반영이 승인된 것은 아닙니다.
- 승인 요청 전에 가능한 로컬 준비·검증과 변경 내용 정리를 끝냅니다. 범위가 달라지거나 민감한 내용이 새로 포함되면 그 차이를 알립니다. 요청 없이 다른 사람에게 메시지를 보내지 않습니다.
- 다른 세션·팀원이 만든 변경을 보존합니다. 같은 파일을 동시에 수정할 때는 범위를 나눕니다. 커밋되지 않은 파일을 덮어써야 하면 먼저 백업하거나 사용자에게 알립니다. 승인 없이 작업을 버리는 reset·clean·강제 덮어쓰기를 하지 않습니다.

### 실행·보안·검증

- 가능한 작업은 로컬 CLI와 직접 실행 가능한 스크립트로 처리합니다. 검색·조회는 필요한 범위로 좁히고, 동일한 확인을 이유 없이 반복하지 않습니다. 연결 도구가 적합한 작업은 현재 제공되는 기능을 확인해 사용합니다.
- 필요한 외부 조회와 공식 문서 확인은 진행합니다. 도구의 현재 기능·버전별 지원 여부를 확인하며, 과거 메모의 기능 제한을 영구 규칙으로 취급하지 않습니다.
- 비밀번호·API 키·인증 토큰·비공개 식별자를 채팅·로그·Git에 노출하지 않습니다. 비밀 파일은 작업에 필요하지 않으면 열지 않습니다. 설정·원격 주소를 조사할 때는 필요한 항목만 읽고 인증 정보가 포함된 원문을 출력하지 않습니다.
- 지침 문서는 실제 실행 권한이나 샌드박스를 변경하지 않습니다. 설정 파일의 존재, 실제 연결 성공, 적용 여부, 작업 결과 검증을 각각 구분합니다. 승인·접근 제한을 우회하지 않습니다.
- 변경한 동작과 위험에 맞는 검증을 실행합니다. 관련 검사에 통과한 뒤에는 새 변경·실패·미해결 우려가 있을 때 추가 검사합니다. 문서 변경에 무관한 게임 실행이나 모든 테스트를 일률적으로 요구하지 않습니다.
- 훅·CI·자동 검사는 해당 환경에서 지원되는 방식과 실제 명령으로 구성합니다. 다른 도구의 설정·이벤트·종료 코드 의미를 그대로 복사하지 않습니다. 도입 시 정상·실패 경로를 확인하고 무한 반복을 방지합니다.
- 절차가 필요한 경우 관련 스킬·스크립트를 사용합니다. 모든 스킬 본문을 상시 지침에 합치지 않습니다. 위임·병렬 작업은 현재 요청과 실행 환경이 허용하는 범위에서만 사용하며, 작업 범위·완료 기준·검증 결과를 공유합니다.

### Git·기록·규칙 관리

- 이어서 작업할 때 변경 상태와 추적 브랜치를 먼저 확인하고, 원격이 있는 저장소는 적절한 작업 브랜치에서 `git pull --ff-only`로 최신 상태를 받습니다. 로컬 변경·분기·네트워크 문제로 실패하면 원인을 보고하고 덮어쓰지 않습니다. 원격이 없는 프로젝트에 pull을 강제하지 않습니다.
- 네트워크 제한으로 로컬 갱신을 못 했을 때 허용된 조회 경로로 원격 내용을 확인할 수 있지만, 이를 로컬 동기화 완료로 보고하지 않습니다. 과거 채팅·메모·오래된 로컬 파일만으로 현재 상태를 단정하지 않습니다.
- 브랜치·리뷰·커밋 형식은 해당 프로젝트 규칙을 적용합니다. 변경 파일과 diff를 확인하고 한 가지 의도로 커밋합니다. PC를 바꾸기 전에는 필요한 로컬 저장·인수인계를 준비하고, 승인된 범위만 push합니다.
- 하루 작업을 마칠 때 인수인계가 필요한 프로젝트는 지정된 이어하기 문서를 갱신합니다. 완료·미완료·검증·다음 단계·미반영 사항을 구분하고, 이전 날짜의 임시 지시를 영구 규칙으로 옮기지 않습니다.
- 공개 데일리 로그·프로젝트 기술 글은 블로그 `Kasil_DevLog`에, 비공개 원문은 노션에 둡니다. 프로젝트 명세·검증 근거·팀 인수인계는 해당 저장소에 유지할 수 있습니다. 같은 글의 원본을 여러 곳에서 따로 수정하지 않습니다.
- 공개 전 연락처·내부 링크·비공개 문서 식별자·미공개 팀 자료를 제거합니다. 노션이나 외부 문서로의 동기화도 외부 반영 승인 범위를 따릅니다.
- 이 통합 원본에서 규칙을 고치고 필요한 범위별 파일을 생성합니다. 수동 수정된 생성 파일은 먼저 비교·보존하고 덮어쓰지 않습니다. 게임 명세와 팀 계약은 지정된 원문에서 관리하며, 그 변경이 작업 규칙에 영향을 주면 이 원본의 해당 범위도 갱신합니다.
- 충돌은 같은 의미의 중복, 적용 범위 차이, 폐기된 과거 지시, 실제 모순으로 나누어 처리합니다. 명시적인 최신 사용자 결정과 현재 팀 합의를 확인하고, 근거가 없으면 임의로 한쪽을 삭제하지 않고 차이를 제시합니다. 플랫폼의 상위 지침·실제 권한은 이 파일로 대체할 수 없습니다.

## Unity 프로젝트 공통

- 프로젝트를 열기 전에 `ProjectSettings/ProjectVersion.txt`와 패키지 상태를 확인합니다. 작업 요청 없이 Unity·렌더 파이프라인·패키지 버전을 올리지 않습니다.
- 에셋 이동·정리는 가능한 Unity의 AssetDatabase를 사용하고 `.meta`·GUID·프리팹 참조를 보존합니다. 이름을 고쳐 쓰기 전에 실제 경로를 확인합니다.
- 씬을 저장한 뒤 변경을 확인합니다. 팀원이 편집 중인 씬·프리팹은 담당자와 순서를 맞춥니다. `Library`, `Temp`, `Logs`, `UserSettings`, IDE 생성물 등은 기존 저장소 제외 규칙을 따릅니다.
- 프로토타입·임시 외형·기능 프리팹·실행 씬 통합의 완료 상태를 구분합니다. 리소스가 들어왔다는 이유만으로 게임 기능까지 완성되었다고 쓰지 않습니다.
- 코드·에셋·씬 변경은 영향에 맞춰 컴파일, 참조, 콘솔, 실행 동작을 확인합니다. 실제 에디터·실행 검증을 할 수 없으면 수행한 정적 검사와 남은 확인을 구분합니다.

## After Seconds

- 사용자 주도의 학습 프로젝트입니다. 요청한 분석·설계·작은 구현 범위를 따르고, 요청 없이 게임 로직·씬·Animator 연결을 먼저 구현하지 않습니다. 코드 작성은 직접 작성과 도구 작성 모두 **의사코드 → 코딩 → 주석** 순서로 진행합니다.
- 현재 명세의 기준은 `Docs/AfterSeconds_메인기획서.md`와 관련 상세 명세입니다. 과거 AGENTS/CLAUDE에 누적된 날짜별 작업 기록은 이력입니다. 최신 사용자 결정과 현행 명세로 대조하며, 과거 실험안이나 코드의 미전환 값을 현행 기획으로 되돌리지 않습니다.
- 작업 재개 시 최신 WorkClose/이어하기의 실제 내용을 확인합니다. 예전 학습 배경 문서는 필요할 때 참고하며, 오래된 파일 하나를 항상 최신 인수인계로 고정하지 않습니다.
- 실제 Unity 루트와 에셋 경로를 확인합니다. 기존 경로 `Unity/After_Seconds_Build_V0.01`, `Assets/Afrer_Seconds`의 철자는 임의로 정정·이름 변경하지 않습니다.
- Unity 개발 방침에 제안(💡)으로 적힌 설계의 상태를 유지합니다. 해당 방침은 순수 C# 예약 큐·명시적인 시간, 순수 데이터와 Step 함수, 실행·미리보기의 판정 공유, Unity 표현·물리 조회 분리입니다. 승인된 구현 범위에서 목적지 공간·지지면·가시선 검사와 이동/감지 Collider의 책임을 구분합니다.
- 고정 설정 데이터와 실행 상태를 구분하고, 사용자가 정한 계층 분리와 현재 데이터 계약을 따릅니다. 엔진·씬·새 이벤트 체계를 필요 이상으로 도입하지 않습니다.
- 아트 에셋 정리 요청에는 분류·이동·출처 기록을 포함할 수 있습니다. 씬 배치·모델 교체·Animator·게임 코드 연결은 요청 범위를 별도로 확인합니다.

### 팀 합의와 Git

- 팀 운영·역할·검토 기준은 저장소의 현재 `README.md`를 따릅니다. 개인 규칙 통합으로 팀 합의 자체를 바꾸지 않습니다. 팀 명세·담당자 변경을 발견하면 이 범위와 원문의 차이를 먼저 확인합니다.

- `main`은 통합 기준이며 backend·frontend·art의 역할 브랜치 운영을 유지합니다. 역할 브랜치끼리 직접 병합하지 않고 main을 거쳐 동기화합니다. PR 후에도 역할 브랜치를 유지합니다. 브랜치 이름에 `#`·공백·한글을 쓰지 않습니다.
- **팀과 합의된 문서만 변경할 때** README·Docs·작업 안내·PR 템플릿은 main에 직접 반영할 수 있습니다. 별도 PR·추가 리뷰를 일률적으로 요구하지 않습니다. 다만 실제 push는 이미 받은 승인 범위를 따릅니다.
- 코드·에셋·씬·프리팹·패키지·프로젝트 설정·CI·배포 변경 및 이들과 섞인 문서 변경은 역할 브랜치와 PR로 처리합니다. Docs 경로나 docs 커밋 타입만으로 실행 코드 변경을 문서 예외로 분류하지 않습니다.
- 구현 PR은 작성자 외 리뷰어 1명 이상과 관련 씬·프리팹 담당자의 확인을 받습니다. 보호 규칙이 직접 push를 막으면 기존 PR 경로를 사용하며 보호 해제·강제 push로 우회하지 않습니다.
- PR 하나에는 기능 하나를 담고 기존 템플릿의 무엇을·왜·변경한 씬/프리팹·검증 방법을 작성합니다. 당일 검토를 기본으로 하되 완료 기준을 건너뛰지 않고 보류 사유·다음 확인 시점을 남깁니다. 마일스톤은 제작 검증 뒤 기존 버전 체계로 태그를 남기며, 하루 두 번 병합 시간은 미확정 제안으로 유지합니다.

### 구현·학습·연결 계약

- 새 스크립트와 기존 로직 변경은 작성 도구·복잡도에 관계없이 **의사코드 → 코딩 → 주석** 순서로 진행합니다. 짧은 로직은 짧게 설계하고, 구현 뒤 설계한 것처럼 꾸미지 않습니다. 구현 흐름이 바뀌면 의사코드·주석을 함께 맞춥니다.
- 파일 헤더에 역할·호출 관계·상태 소유를, 공개 멤버와 직렬화 필드에 목적·단위·범위를 설명합니다. 숫자 값을 주석에 중복 관리하지 않고, 코드만으로 알기 어려운 판단·예외의 이유를 적습니다. 담당자가 의사코드와 실제 동작을 대조해 설명할 수 있어야 합니다.
- 5계층을 지킵니다: Define(0, 독립), Utils(1 → Define), Systems(2 → 0·1), UI(3 → 0·1), Manager/Presenter(4 → 하위 계층). UI와 System은 직접 참조하지 않고 Manager·Presenter가 연결합니다. 현재 DOB asmdef/asmref의 방향을 확인합니다.
- 게임 상태는 담당 System 하나가 소유합니다. UI·Manager에 금화·재고·주문 같은 상태를 중복 저장하거나 판정을 중복 구현하지 않습니다. ScriptableObject 기준 데이터, 실행 상태, 저장 데이터를 구분합니다.
- 요청은 안정적인 ID와 필요한 입력을 전달합니다. 선택 UI의 인덱스·표시 이름에 의존하지 않습니다. 요청의 결과·실패 사유를 명확히 하며, 실패한 요청은 재화·재고·상태를 부분 변경하지 않습니다. 중복 입력·정산은 상태 소유자가 한 번만 처리합니다.
- 미리보기와 실제 판정은 같은 계산 규칙을 사용하고, UI에는 사용자가 알 수 있는 정보만 표시합니다. View는 실제 상태·결과를 읽으며 UI 타이머가 게임 완료를 따로 판정하지 않습니다.
- 구독·해제는 같은 수명 범위로 짝을 맞춥니다. 복구 → System 준비 → Presenter 연결 → View 표시의 준비 상태를 명시하고 Awake/Start의 우연한 순서에 의존하지 않습니다. 미준비·실패·이미 처리된 상태를 정상값으로 표시하지 않습니다.
- 객체 연결은 인스펙터나 조립 단계에서 전달하고 Find 계열 임의 검색에 의존하지 않습니다. 이벤트 버스를 상태 저장소로 사용하지 않습니다. 화면을 다시 열면 현재 상태를 조회하고 과거 이벤트·보상을 다시 실행하지 않습니다.
- 비동기 완료 시 화면·주문·대상의 유효성을 확인합니다. 종료·씬 전환 시 구독·진행 작업·참조를 정리합니다. 시간·저장·회복 시점은 최신 기획 계약을 따르고 통합 지침에서 새 기획을 확정하지 않습니다.
- 사운드 시스템 구현, UI 요청/음량 연결, 음원 수급·라이선스 확인의 책임과 완료 기준을 구분합니다. 입력음과 실제 성공 효과음을 구별하고, 거절·반복 입력·화면 재열기·복구로 성공 효과음을 다시 재생하지 않습니다. 현재 담당은 README와 EngineeringGuide에서 확인합니다.
- 로직은 가능한 순수 C#으로 검증하고 Editor/PlayMode 검증의 범위를 구분합니다. 현재 오프라인 프로젝트에 서버·DB·대규모 데이터 파이프라인을 임의로 도입하지 않습니다.
- 클래스·메서드·프로퍼티는 PascalCase, 인스펙터 노출은 `[SerializeField] private`, 파일 하나에 MonoBehaviour 하나와 같은 파일명/클래스명을 적용합니다. private 필드의 camelCase·밑줄 제외는 README의 제안(💡) 상태를 유지하며 합의 전 강제하지 않습니다.

### 문서·에셋·완료 기준

- 일정·작업 카드는 노션, 버그는 GitHub 이슈, 변경·리뷰는 PR로 관리하며 링크로 연결합니다. 같은 상태를 여러 트래커에서 따로 유지하지 않습니다. 작업 카드에는 담당·입출력·수용 기준·검증을 명시합니다.
